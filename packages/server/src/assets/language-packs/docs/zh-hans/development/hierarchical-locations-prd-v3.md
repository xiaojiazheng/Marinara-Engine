# 分层地图与空间上下文 V3

状态：提案，维护者批准后即可进入实现阶段

读者：产品、设计以及 Marinara Engine 贡献者

取代：`hierarchical-locations-prd-v2.md`

## 架构边界

本方案把空间定位当成一项目标明确的产品能力，状态边界收得很窄。

这项功能是分层地图与空间定位系统，不是 Voxta 那样的通用剧情引擎。它只借用了 Voxta 的一个有用做法：用持久化状态挑出一小段相关的提示词上下文。初期不引入标志位、变量、事件、脚本、计时器，也不引入独立的行为推断模型。

支持的归属模式是 Roleplay 和 Game。

方案分为五个职责明确的层：

| 层 | 职责 | 示例 |
| --- | --- | --- |
| 地图定义 | 稳定的空间事实 | 图书馆位于法师塔内部 |
| 运行时状态 | 当前场景所在地点 | 场景当前位于图书馆 |
| 提示词投影 | 范围受限的模型定位信息 | 面包屑、当前记忆、可达出口 |
| 视觉标识 | 可选的地点专属美术参考 | 图书馆在不同场景中保持相同的拱门、窗户和材质 |
| 转移 | 经过校验的状态变更 | 从图书馆移动到天文台 |

状态机刻意做得很小：

```text
current location + requested destination + definition revision
                              ↓
                  validate ownership and reachability
                       ↙ accepted       rejected ↘
              persist snapshot         preserve state
```

首先上线的是手动移动。之后，受限的模型工具（例如 `change_location({ destinationId })`）也可以请求同一个转移。校验和落地由服务器完成，不交给模型。独立的行为推断调用暂缓，除非后续证据表明确有必要。

## 摘要

为 Roleplay 和 Game 增加一项共用的分层地图功能。它提供由作者定义的地点层级、唯一权威的焦点地点、范围受限的当前地点提示词上下文，以及由服务器校验的移动。

可复用的世界设定事实仍以世界书为准。层级可以通过稳定 ID 引用已有的世界书条目，这样当前地点就能挑出相关设定，既不复制也不改写。AI 起草地图时可以把显式选定的世界书当作有据可依的素材，并且必须把有出处的地点和推断或虚构出来的地点区分开。

地点还可以拥有一套可选的视觉标识：一段简短的视觉锚点描述，加上指向档案图库图片的稳定引用。地点始终是空间实体，不是一张图片。聊天的图像风格方案决定整体渲染风格，地点参考图保住场所本身，角色或用户角色参考图保住场所里的人。

关联的 Conversation 之后可以读取所链接故事地点的安全投影，但它永远不拥有、也不改动空间状态。

```text
authoritative hierarchy + current location
                    ↓
resolve breadcrumb, context, and valid destinations
                    ↓
build the mode-specific prompt
                    ↓
commit a validated move with the next owner turn
                    ↺
```

这不是通用剧情引擎。它不引入标志位、事件、作者编写的 JavaScript，也不做寻路。但它确实包含一个可视化的嵌套地图浏览器，支持地图、分层和列表三种呈现方式。

## 产品决策

以下决策回答了 V2 遗留的开放问题：

1. 层级定义和当前地点分开存储。
2. 当前地点随已提交的消息和备选回复状态一起快照，因此分支、重新生成和存档点都能恢复到正确的位置。
3. 手动移动与下一次归属模式的用户回合原子提交，时机在生成提示词之前。
4. 启用后，Spatial Context 就是权威。Game 原有的自由文本地点不能变成第二个事实来源。
5. Roleplay 和 Game 共用一套空间投影契约，各自只加一层很薄的模式专属提示词适配器。
6. `awarenessSummary` 由作者撰写。缺失时，Conversation 只收到公开描述的一段受限摘录。
7. 除非权威的在场数据能证明所关联的角色在场，否则 Conversation 一律使用场景级别的措辞。
8. 直连链接和子地点的可视化摆放都包含在 MVP 中。
9. 已有的 Game 网格地图和节点地图可以显式绑定到层级地点；名称永远不会自动匹配。
10. 世界书拥有可复用的权威世界设定事实；地图拥有空间标识、包含关系、导航和当前地点状态。地图地点通过稳定 ID 引用世界书条目，绝不复制其内容。
11. 地点挂载是一种显式的、聊天范围内的激活来源。只要当前正好处在该地点，它挂载的已启用条目就可以在没有关键词命中的情况下激活，但已禁用或被显式排除的世界书和条目仍然保持禁用。
12. 基于世界书的地图起草跟随归属模式的运行时界面，先于关联 Conversation 落地。选定了来源世界书之后，草稿必须标明哪些地点有出处、哪些是推断的、哪些是凭空添加的，而不是把没有依据的地理信息当成正典呈现。
13. 地点永远不会被一张图片取代。它可以通过稳定的图片 ID 引用可选的视觉标识素材，其中一张主图作为定场参考，另有数量受限的辅助参考图。
14. 地点视觉参考只进入符合条件的图像生成路径。文本生成、世界设定激活和关联 Conversation 永远拿不到图片字节或仅供图像使用的备注。
15. 分镜是同一套视觉解析器的下游消费方。每个分镜都会冻结一份锚定到具体消息和备选回复的参考清单，这样之后重新生成时就不会悄悄换用更新的地点或角色美术素材。
16. 由模型发起的移动仍属于后续阶段。

## 使用体验

### 编辑

Chat Settings(聊天设置) 里有一块紧凑的 Spatial Context 区域，包含：

- 启用状态
- 当前面包屑
- 地点数量和警告数量
- 打开地点编辑器的入口

编辑器是一个懒加载的地图工作区，不是一张狭窄的设置表单：

- 桌面端使用层级面板、局部地图或分层视图，以及地点详情面板。
- 移动端一次只显示一个面板，并提供清晰的返回导航。
- 校验提示出现在对应输入框或节点旁边。
- 保存状态和修订冲突始终可见。
- 归档是主要的移除操作；硬删除受到限制。
- 选中只是预览一个地点。进入用单独的 Enter 操作，这样点击就不会同时含糊地表示查看、编辑和移动三件事。
- 每个父地点都把子地点呈现为带坐标的地图、有序的分层，或者一份可访问的列表。
- 复制子树让创作者可以复用已有结构，MVP 阶段无需依赖跨聊天模板。
- 每个地点都有一块渐进展开的 `Linked lore` 区域，可以搜索已有的世界书条目，标出已禁用或缺失的引用，并支持打开条目和解除挂载，全程不复制也不删除任何世界设定内容。
- 每个地点都有一块渐进展开的 `Visual identity` 区域，包含主图、辅助参考图、用法备注，以及明确的图库选择、上传和生成操作。图片永远不会取代地点名称、图标或无障碍导航标签。

### 基于世界书的起草

当归属聊天已选中或启用了世界书时，AI 地图生成器会提供世界书取材选项。取材过程是显式且可查验的，不是普通的关键词扫描。

- Game 的设置流程把 Lorebooks(世界书) 步骤里选中的世界书作为默认地图来源。
- Roleplay 把当前聊天已启用的世界书作为默认来源，创作者可以在地图生成器里改选。
- `Strict canon` 要求每个具名节点至少来自一条选定的世界设定条目。它宁可保留多个各有出处的根节点，也不会虚构没有依据的中间地点。
- `Canon with expansion` 保留有出处的名称和关系，同时允许添加明确标注的推断或虚构地点来填补实际需要的空缺。
- `Setup only` 保持原有行为，只使用设置信息、世界概览、故事线、剧情设定和角色上下文，不做世界书取材。
- 存在选定的世界书时，`Canon with expansion` 是更易上手的默认项。对于重度使用世界书的创作者，`Strict canon` 也只有一步之遥。

草稿预览里的每个生成节点都会标出 `Lore-backed`、`Inferred` 或 `Added by AI`。有出处的节点会列出来源条目，并提供打开条目的入口。这个标记只能证明存在有效的来源引用，不能证明模型准确理解了原文，所以语义上的最终判断仍然归创作者审阅。应用只改动本地工作副本，保存才是持久化的分界线。

### 地点视觉标识与参考美术

地点图片应当提升场景一致性，但不能把层级变成图库，也不能让它变成又一个空间事实来源。

- 创作者可以上传图片、选用档案图库里已有的图片、把生成的场景图提升为参考图，或者根据地点的面包屑、公开描述、视觉锚点、挂载的世界设定和选定的图像风格方案生成一张定场参考图。
- 挂载聊天图库图片、生成的 Game 背景或其他临时来源时，系统会先创建一份持久的档案图库素材。地图存的是稳定的图库图片 ID，绝不是文件路径、外部 URL 或 base64 数据。
- 可以指定一张 `identity` 图片作为主图。辅助图片可以用来表现某个标志性细节、另一个视角、布局，或者可继承的美术风格线索。
- `layout` 参考图默认只是编辑器里的辅助材料，除非专门的背景或平面图请求明确要用它们。它们不会自动进入普通场景插画，因为容易扰乱构图。
- 只有 `style` 参考图可以选择向下级继承。标识图和细节图只作用于该地点本身，所以城市天际线不会悄悄变成里面每个房间的视觉标识。
- 生成的场景美术不会自动成为正典。`Set as location reference` 是一个显式的审阅操作，避免反复生成把偶然细节或风格偏移越滚越大。
- 选中地点的详情面板会显示主图和各参考图的角色。密集的层级视图和地图视图仍以名称为主，空间允许时可以显示小缩略图，但导航永远不依赖看图辨认。
- 图像生成预览会列出解析出的每一张地点和角色参考图、它的角色，以及因服务商上限而被略去的参考图。它不会在诊断信息里记录或显示原始 base64。

理想的一致性堆栈是：

```text
chat image style profile  -> shared rendering language
current location refs     -> stable architecture and place identity
character/persona refs    -> stable people and appearance
scene prompt              -> current action, framing, weather, and lighting
```

参考美术是视觉证据，不是自动生成的世界设定。添加图片永远不会创建地点、改变包含关系或写入世界书事实。从图片反推地图仍是需要单独审议的后续工作流。

### 分镜的参考连续性

分镜应当消费已完成的 GM 回合中经过审阅的视觉标识，但空间功能本身不能反过来依赖分镜。

- 档案图库和各实体图库构成一个参考库，其中可以为一个地点、角色或用户角色存放多张已审阅的图片。生成关键帧时，只会从这个库里挑出与服务商容量相匹配的一部分作为参考。
- 创建分镜时会解析其来源消息和备选回复对应的确切空间快照。绝不会拿聊天最新的地点去顶替更早的回合。
- 分镜会把解析出的地点、有序的候选图片 ID、每个关键帧的选择结果、略去项和服务商容量冻结进一份视觉参考清单。重新生成会一直复用这份清单，直到创作者明确选择 `Refresh references`。
- 同一张地点主图对每个关键帧都可用。角色和用户角色的候选图则随该帧的可见角色列表变化，这样不在画面里的成员就不会占用参考名额。
- 第一版会为每个出镜实体自动选一张主图，外加最多一张辅助地点图片。更丰富的参考库仍然可以用于手动挑选，以及将来按镜头匹配角度、服装、表情或细节，但 Marinara 不会在每一帧都把所有存图发出去。
- 如果只剩一个自动名额，有可见角色的关键帧选主要出镜角色，没有可见角色的定场关键帧选地点主图。剩两个或更多名额时，先选地点主图，再补可见角色参考图。
- 换用容量更高的服务商不会悄悄给已有分镜添加参考图。换用容量更低的服务商则会产生一条内联的 `Review references` 冲突提示，而不是悄悄改动已冻结的内容。
- 每个关键帧预览都有一块渐进展开的 `Visual sources` 区域，列出解析出的地点、选中的角色、图片角色、排序和略去原因。`Refresh references` 就在那里，无需额外的分镜素材管理器，也不会弹出阻塞式窗口。
- 生成的关键帧永远不会自动变成角色或地点参考图。已有的显式提升操作仍是唯一的持久化分界线。

### 运行时移动

归属模式的聊天界面会显示：

- 已持久化的当前面包屑
- 有效目的地选择器
- 标注清晰的待生效目的地

选中目的地并不会立刻改变权威状态。发送下一条消息时，目的地 ID 和期望的修订号会和可见的消息文本分开提交。服务器先提交这次移动，再组装回复提示词。

如果校验失败，消息和移动都不会部分提交。客户端保留草稿并说明冲突原因。

## 数据模型

定义存放在聊天元数据里。运行时位置存放在快照历史里。

```ts
export type SpatialOwnerMode = "roleplay" | "game";

export type LocationVisualReferenceRole = "identity" | "detail" | "layout" | "style";

export interface LocationVisualReference {
  imageId: string;
  role: LocationVisualReferenceRole;
  primary?: boolean;
  usageNote?: string;
  inheritToDescendants?: boolean;
  sortOrder: number;
}

export interface ChatLocation {
  id: string;
  name: string;
  parentId: string | null;
  description: string;
  kind: "region" | "settlement" | "place" | "building" | "floor" | "room";
  modelMemory?: string;
  icon?: string;
  childPresentation: "map" | "layers" | "list";
  placement?: { x: number; y: number };
  layerOrder?: number;
  awarenessSummary?: string;
  visualIdentity?: string;
  visualReferences: LocationVisualReference[];
  lorebookEntryIds: string[];
  links: ChatLocationLink[];
  status: "active" | "archived";
  sortOrder: number;
}

export interface ChatLocationLink {
  targetId: string;
  label?: string;
  bidirectional: boolean;
  state: "available" | "hidden" | "blocked";
}

export interface SpatialContextDefinition {
  schemaVersion: 1;
  ownerMode: SpatialOwnerMode;
  enabled: boolean;
  locations: ChatLocation[];
  startingLocationId: string | null;
  revision: number;
}

export interface SpatialContextSnapshot {
  id: string;
  chatId: string;
  messageId: string;
  swipeIndex: number;
  currentLocationId: string | null;
  definitionRevision: number;
  createdAt: string;
}

export interface PendingSpatialTransition {
  destinationId: string;
  expectedDefinitionRevision: number;
  expectedCurrentLocationId: string | null;
  commandId: string;
}
```

不要把 `ownerChatId` 存进 `SpatialContextDefinition`；所在的那个聊天就是归属方。稳定的不透明 ID 在改名和更换父节点之后依然有效。

第一版归属 MVP 把缺失的 `lorebookEntryIds` 或 `visualReferences` 字段当成空数组，这样后续版本可以扩展 schema 版本 1，而不必急着重写已有定义。条目引用和图片引用都只存稳定 ID。世界书名称、条目名称、关键词、内容、图片路径和图片字节都在使用时才解析，绝不复制进空间定义。`imageId` 通过持久的档案图库解析；挂载临时图片或聊天范围的图片时，会先提升出一份持久副本。

## 图规则

有效目的地必须处于活跃状态，且属于以下之一：

- 当前地点的子地点
- 当前地点的父地点
- 直连链接的目标
- 双向链接的反向目标

同级地点之间不会自动相邻。

以下情况一律拒绝：

- ID 重复
- 父地点或链接目标缺失
- 自己作父地点，或父级成环
- 地点超过 500 个
- 深度超过 20
- 单个地点的链接超过 50 条
- 单个地点的世界书条目引用超过 50 条
- 同一地点上出现重复的世界书条目引用
- 单个地点的视觉参考超过 6 张
- 同一地点上出现重复的视觉图片引用
- 出现多张主视觉参考图，或主参考图的角色不是 `identity`
- 在 `style` 以外的角色上启用向下级继承
- 摆放坐标超出 0 到 100 的范围
- 同一分层父节点内出现无效或重复的分层序号
- 移动到已归档、隐藏、阻断或不可达的地点
- 修订号过期，或当前地点已发生变化
- 复用的命令 ID 携带了不同内容
- 来自 Conversation 的修改尝试

文本长度上限：

- 名称：200 个字符
- 描述：4,000 个字符
- 感知摘要：1,000 个字符
- 私有模型记忆：8,000 个字符
- 视觉标识：800 个字符
- 视觉参考用法备注：300 个字符

直连链接成环是合法的。父级成环则不合法。

### 归档与删除

- 归档之前，当前地点或起始地点需要一次原子的替换。
- 还有活跃子地点的地点不能归档。
- 只有没有入向链接的已归档叶子节点才允许硬删除。
- 后代节点永远不会被悄悄改挂到别处。
- 缺失的世界书引用只会显示为警告，不算图结构损坏。
- 归档或删除地点永远不会删除它引用的世界书条目。
- 删除世界书或条目也永远不会悄悄改写地图。地点会保留一条可修复的断裂引用，直到创作者解除挂载或换成别的条目。
- 归档或删除地点永远不会删除共享的档案图库图片。
- 如果某张图库图片仍被某个地点或某份已冻结的分镜清单引用，删除会被阻止，直到创作者解除挂载或刷新每一份依赖它的清单。缺失的图片引用始终是可修复的警告，绝不会退化成原始路径。

## 持久化与历史

### 定义

把 `SpatialContextDefinition` 存在 `chat.metadata.spatialContext` 里。更新定义必须带 `expectedRevision`；更新被接受后修订号加一。

### 运行时位置

按现有的 Game State 快照模式，用可按消息和备选回复寻址的快照存储当前位置。

- 新建的归属聊天从 `startingLocationId` 开始。
- 每次提交回合都会在移动被接受之后创建一份快照。
- 重新生成把位置关联到生成出来的那条备选回复。
- 切换备选回复会解析到对应的快照。
- 在某条消息处分支时，复制的是那个时点生效的快照，而不是源聊天的最新位置。
- Game 存档点会引用或包含对应的空间快照。
- 重新加载时解析最近一次提交的快照。

MVP 阶段，普通的消息分支不会回退定义的编辑。分支会拿到当前定义的一份副本，之后各自独立记录修订历史。它的运行时位置来自分支点。

## 提示词投影

由服务器端一个共享的投影服务解析出结构化的投影数据。各模式的薄适配器再把它变成最终的提示词文本。

### 归属模式的故事投影

包含：

- 面包屑名称
- 当前地点 ID
- 公开描述
- 当前地点的私有模型记忆
- 可用目的地的名称、ID 和链接标签
- 一条说明该状态为权威的指令

排除所有无关地点的描述和记忆、隐藏或阻断的目的地、画布坐标以及编辑器元数据。

### 当前地点的世界设定激活

归属模式的空间解析器会在返回常规空间投影的同时，返回当前地点确切的 `lorebookEntryIds`。格式化器不会把这些 ID 或条目内容粘贴进空间块。取而代之的是，提示词组装环节把这些 ID 作为强制候选传给已有的世界书处理器，激活来源标记为 `current_location`。

规则：

- 首个版本里只有当前所在的确切地点会激活挂载的世界设定。父地点和后代地点不会隐式继承条目。
- 即使某本世界书既不是全局的，也没有关联角色或用户角色，更没有固定到当前聊天，显式的地点挂载依然可以激活其中已启用的条目。
- 全局禁用的世界书、禁用的条目，或聊天级别的显式排除，优先级永远高于挂载。
- 已有的世界书宏、插入位置、递归、排序以及每本书的 Token 和条目上限都照常复用。
- 地点挂载的世界设定在每次归属模式提示词里另有 2,048 个 Token 的总预留上限。截断方式是确定的，并会在 Active Context 中体现。
- 同时被地点激活和普通关键词、语义、递归或常量规则激活的条目只注入一次，但会报告全部激活来源。
- 移动一旦提交，就会在组装归属模式回复提示词之前解析目的地的条目。待生效或被拒绝的移动不会改变世界设定激活。
- Game 的措辞把该地点当作队伍的权威位置。Roleplay 的措辞把它当作焦点场景，不会推断每个角色都在场。

Active Context 界面会把这些条目归到 `Current location` 分组下，显示所属世界书、激活来源、Token 用量或截断情况，并提供打开条目的入口。断裂、禁用和被排除的引用在地图编辑器里仍然可见，但永远不会进入提示词。

### 关联 Conversation 的投影

在阶段 3 加入。只包含：

- 所链接故事的名称和模式
- 面包屑
- `awarenessSummary`，或一段受限的公开描述摘录
- 只读指令
- 只有权威状态能证明时，才包含角色在场信息

绝不包含私有模型记忆、内部 ID、隐藏目的地、完整层级、地点挂载的世界书 ID 或内容、地点视觉参考 ID、视觉标识备注、用法备注、图片路径或图片字节。

Game 可以通过已提交的 `presentCharacters` 状态来证明在场。Roleplay 在拿到明确的在场数据来源之前，只使用中性措辞，例如“The linked story's current scene is…”永远不要靠角色名推断在场。

### 必须覆盖的提示词路径

同一个投影解析器必须为以下路径供数：

- Roleplay 生成
- Game 的 GM 生成
- 试运行预览
- 实时 Peek Prompt 组装

缓存的 Peek Prompt 仍然显示当初实际发出的那份提示词。调试日志包含最终投影，但在普通级别下不得记录私有模型记忆。

### 供图像生成使用的当前地点视觉投影

视觉参考使用与故事提示词不同的解析器。它解析的是与目标图片相对应的空间快照，而不是聊天最新的地点。Game 的自动美术使用为该 Assistant 消息提交的那份快照。为更早的备选回复重试出图，或从更早的消息调用 Illustrator，都使用那条消息和那条备选回复解析出的地点。

符合条件的路径有：Game 自动场景美术、Game 手动场景插画，以及在按聊天设置的地点参考开关开启时的 Roleplay Illustrator 场景或背景生成。头像、自拍、头像图和立绘生成不会自动附带地点参考。

有两个聊天元数据开关与已有的头像参考开关一一对应：`illustratorUseLocationReferences` 和 `gameImageUseLocationReferences`。字段缺失或为 false 一律视为关闭，以保证向后兼容。创作者设置第一张地点主图时，同一次保存流程会提供 `Use this location in scene art`，默认勾选但需要明确确认，这样就不会仅仅因为地图编辑器里显示了一张图片，就把图片字节发给服务商。

候选顺序是确定的，并会考虑服务商能力：

1. 本次出图请求显式选定的参考图。
2. 解析出的确切地点的主 `identity` 参考图。
3. 按场景顺序排列的相关角色和用户角色。
4. 该确切地点按 `sortOrder` 排序的辅助 `identity` 和 `detail` 参考图。
5. 最近祖先地点的可继承 `style` 参考图。

不允许任何同级回退或按名称回退。普通场景请求最多有两张地点图片作为候选，之后由已有的服务商适配器套用它自己的图片总数上限。显式请求的参考图永远优先占用名额。剩下的自动名额里，背景请求优先保地点标识而非角色参考，插画请求则先选地点主参考图，再补其他出镜人物参考图。如果服务商无法同时容纳场所和全部指定人物，预览会说明这次确定性的取舍以及每一条略去原因。

图像提示词编译器会加入地点面包屑、长度受限的 `visualIdentity`，以及每张选中参考图长度受限的 `usageNote`。风格仍以聊天选定的 `ImageStyleProfile` 为准。参考图只负责保住场所或主体的身份特征，不得悄悄替换风格方案里的风格文本、正向标签、负向标签或提示词模式。

参考图的角色表达的是创作者意图和选择优先级，并不保证每家服务商都会把一张图理解成标识、细节、布局或风格。服务商能力说明和生成预览让创作者始终掌握视觉上的最终决定权。

发给文本模型的请求拿不到这些图片字节，也拿不到仅供图像使用的用法备注。关联 Conversation 既拿不到视觉参考 ID，也拿不到其内容。图像调试日志可以包含图片 ID、地点 ID、角色、选择理由和略去项，但绝不包含 base64 或文件系统路径。

### 分镜视觉参考清单

分镜适配器在 GM 回合完成、其消息和备选回复提交之后，一次性解析出视觉候选。它会存下一份冻结的参考库，以及为每个关键帧挑选的、符合服务商容量的实际内容。这样就把持久的参考身份和那份可能只接受一小部分的服务商请求分开了。

选择过程是确定的：

1. 关键帧上显式指定的参考图优先占用名额。
2. 只剩一个自动名额时，定场帧选地点主图，有可见角色的帧选主要出镜角色。
3. 剩两个或更多自动名额时，先选确切地点的主图，再按叙事顺序为每个可见角色或用户角色各选一张主参考图。
4. 还有余量就依次用于：一张该确切地点的辅助标识图或细节图、次要出镜实体的参考图、最近的可继承地点风格图。

分镜永远不会隐式拼出拼图页或合成参考图。这类手法会改变服务商的理解方式，留作将来针对特定服务商的优化。图片缺失、更换服务商或服务商上限下降，都会把清单标记为 `needs_review`，而不会悄悄改选另一个实体。容量提高时同样保留已冻结的内容，直到确认执行 `Refresh references`。

清单存的是 ID、标签、角色、排序、选择理由、略去原因、来源消息和备选回复、解析出的地点 ID、定义修订号、服务商标识以及所用的参考数量上限。它不存图片字节或文件系统路径。调试输出可以描述这份清单，但同样遵守普通图像生成那套“不含 base64、不含路径”的规则。

## Game 兼容性

已有的 Game 网格地图和节点地图仍然是局部或战术层面的表示。层级则成为它们之上的世界层和包含关系层。

启用 Spatial Context 之后：

- Spatial Context 向提示词提供权威的具名地点。
- Game 追踪器把空间面包屑显示为它的地点。
- 原有的模型补丁或手动补丁不能自行改动 Game 的自由文本地点。
- `GameMap.spatialLocationId` 可以把整张地图绑定到一个层级地点。
- `GridCell.spatialLocationId` 和 `MapNode.spatialLocationId` 可以绑定一个可进入的目的地。
- 绑定只使用稳定 ID；名称永远不会自动匹配。
- 选中已绑定的目的地所产生的待生效转移，与在层级浏览器里操作完全一样。
- 在未绑定的格子或节点之间移动只改变战术层面的队伍位置。
- 进入某个地点时可以选中它绑定的局部地图；离开时可以选中最近的已绑定祖先地图。

未启用时，Game 原有的地点行为保持不变。

这条边界既保住了当前的地图界面和存档，又避免出现两个具名空间事实来源。

## API 形态

```text
GET  /api/chats/:chatId/spatial-context
PUT  /api/chats/:chatId/spatial-context
```

更新定义：

```ts
interface UpdateSpatialContextRequest {
  expectedRevision: number;
  expectedCurrentLocationId: string | null;
  replacementCurrentLocationId?: string | null;
  definition: SpatialContextDefinition;
}
```

`replacementCurrentLocationId` 只在一次定义编辑归档了当前生效地点时才用得上。服务器必须在写入定义修订的同一次写操作里校验并应用这个替换。普通移动仍然走归属模式的回合提交。

待生效的移动通过已有的归属模式回合请求提交，不设单独的即时转移接口。

服务器在与消息提交相同的事务内校验定义完整性、归属模式、期望修订号、期望当前地点、可达性和命令幂等性。

状态过期返回 `409 Conflict`，图结构或目的地无效返回 `400 Bad Request`。错误信息不得泄露隐藏目的地。

## 实现计划

### 阶段 0：共享核心与验证夹具

- 添加共享类型和 Zod schema。
- 添加纯函数式的图校验、面包屑和目的地辅助函数。
- 为合法与非法图各添加一组确定性夹具数据。
- 确认 Roleplay 和 Game 的消息/备选回复快照集成点。
- 测量有代表性的提示词投影体积。

退出条件：无需界面即可证明 schema、移动语义和快照行为成立。

### 阶段 1：归属模式 MVP

1. 添加带乐观并发控制的定义持久化。
2. 添加空间快照的存储与解析。
3. 把原子的待生效移动集成进归属模式的回合提交。
4. 处理重新加载、备选回复、分支和 Game 存档点。
5. 把共享投影服务接入每一条必需的提示词路径。
6. 添加紧凑的设置区域、层级导航器、局部地图画布、分层选择器和编辑器工作区。
7. 在归属模式界面加入面包屑、目的地选择器、预览和待生效状态。
8. 通过稳定的地点 ID 绑定已有的 Game 地图、格子和节点。
9. 启用时同步 Game 追踪器的地点显示。

退出条件：Roleplay 和 Game 能基于同一套空间模型完成编辑、移动、持久化、恢复和提示词构建。已绑定的 Game 地图移动与未绑定的战术移动保持区分。

### 阶段 2A：地点世界书绑定与运行时

- 给地点添加 `lorebookEntryIds`，默认兼容为空数组。
- 在地点编辑器里加入内联的挂载、打开、解除挂载，以及禁用、排除和断裂引用状态。
- 通过已有的世界书处理器，把确切当前地点的引用解析为强制候选。
- 复用常规的宏、插入、递归、排序和每本书上限；再加上确定性去重和 2,048 个 Token 的地点设定总上限。
- 在 Active Context 里把 `current_location` 与关键词、语义、递归或常量激活来源一并报告。
- 证明 Roleplay 和 Game 行为完全一致，涵盖移动、重新加载、重新生成、备选回复和分支。
- 证明关联 Conversation 既拿不到地点世界设定 ID，也拿不到其内容。

退出条件：创作者可以显式把已有世界设定绑定到地点，且只有被接受的当前地点会在归属模式提示词里激活这些条目。

### 阶段 2B：基于世界书的地图起草

- 为创建、替换和历史安全的扩展请求加上取材模式，以及显式的世界书或条目来源选择。
- 这次编辑操作直接读取选中的已启用世界设定条目，不依赖关键词激活，也不依赖生成出来的世界概览。
- 构建一份考虑连接上下文、体积受限的来源目录，带可见的略去数量和确定性排序。
- 给模型临时的来源键，服务端校验返回的每一个键，只持久化稳定的条目 ID。
- 支持 `setup_only`、`lore_strict` 和 `lore_expand` 三种行为，预览中带来源标注。
- 把有效的来源条目自动绑定到生成的地点上，同时把应用和保存保留为两道独立的审阅关口。
- 仅追加式扩展期间，保留每一个已有的地点 ID 和世界设定绑定。

退出条件：熟悉世界书的创作者可以直接依据选定的正典生成地图，识别出每一处没有依据的添加，并在持久化之前拒绝或修改它。

### 阶段 2C：地点视觉标识与场景参考

- 添加长度受限的 `visualIdentity` 和 `visualReferences` 字段，默认兼容为空。
- 复用持久的档案图库图片 ID，以及已有的安全图库上传、元数据和图像生成路径。定义中绝不持久化原始路径、外部 URL 或 base64。
- 添加按聊天设置的 Illustrator 与 Game 两个并列的地点参考开关。首张主图的保存流程会先取得明确同意，再允许发给服务商。
- 只基于长度受限的确切地点上下文和已启用的挂载世界设定生成定场参考图。不扫描无关的世界书或层级分支。
- 在地点编辑器里加入内联的主图、辅助图、角色、用法备注、图库选择、上传、生成、解除挂载、断裂引用和反向链接状态。
- 把该消息和备选回复的确切地点解析进符合条件的 Game 与 Roleplay 场景美术请求，然后在服务商各自的上限下合并地点、角色、用户角色和显式参考。
- 为生成的美术添加显式的 `Set as location reference` 提升操作。绝不自动提升生成的场景图。
- 让视觉参考 ID 在分支和 JSONL 元数据导出中得以保留，目标缺少素材时给出警告，并把素材纳入档案备份与恢复。
- 证明故事提示词和关联 Conversation 既拿不到地点图片 ID、字节、路径，也拿不到仅供图像使用的备注。

退出条件：创作者可以从视觉上确立一个场所，生成多张复用其已审阅标识的场景图，清楚看到实际发出了哪些视觉参考，并且在移除或替换这些参考时不改变空间或世界设定层面的事实。

### 阶段 2D：分镜视觉参考清单

- 在阶段 2C 的视觉解析器外面加一层下游分镜适配器，而不是把空间持久化和分镜耦合在一起。
- 解析来源消息和备选回复对应的空间快照，然后冻结地点与实体参考库，以及每个关键帧的服务商内容。
- 容量允许时在各关键帧之间复用同一张确切地点主图，同时从每一帧的可见角色列表里挑选角色和用户角色参考。
- 持久化服务商标识、参考容量、有序选择结果和略去原因，让重新生成可复现。
- 在分镜预览和重新生成流程里加入内联的 `Visual sources`、`Review references` 和显式的 `Refresh references` 状态。
- 图片缺失或服务商容量缩水时，拒绝悄悄重选。不要自动填满新腾出的容量。
- 让清单在已有的分镜生命周期中得以保留，并证明关键帧转视频仍然只把渲染出的关键帧作为首帧输入。

退出条件：每个分镜关键帧都能说明并复现自己的视觉输入，重复出现的画面共享正确的历史场所标识，服务商限制永远不会悄悄替换地点或出镜人物。

### 阶段 3：关联 Conversation

- 生成时通过 `connectedChatId` 解析最新的归属模式状态。
- 添加范围受限的只读投影。
- 使用保守的在场措辞。
- 即便归属模式生成用到了这些数据，也要排除地点挂载的世界设定 ID 和内容、视觉参考 ID 和元数据、图片路径以及图片字节。
- 覆盖解除关联、重新关联、归属方被删除、链接损坏、故事已完结，以及地点世界设定的反向验证。

### 阶段 4：由模型发起的移动

- 为归属模式添加带类型的 `change_location` 请求。
- 套用同样的修订号、可达性和幂等性校验。
- 在调试诊断中记录被接受和被拒绝的请求。
- Conversation 仍然无法请求转移。

### 阶段 5：创作者模板

- 保存并导入可复用的地点子树或整张地图。
- 在明确归属和合并行为之后，允许创作者随角色一起发布起始地图。
- 复制到另一个聊天时生成新的 ID，同时保留内部引用关系。

## 仓库实现蓝图

规划基线：`hierarchical-locations` 分支，于 2026-07-13 合并 `staging` 的 `4fd752ea` 之后。在这个基线上，分支里只有 V1、V2 和 V3 三份规划文档。Spatial Context 的运行时代码尚不存在。

### 已确认的集成约束

| 关注点 | 仓库当前行为 | 实现上的后果 |

### 持久化契约

定义仍留在聊天元数据里，分支复制聊天元数据时会自动带上。运行时状态则单独用一张表：

```ts
interface SpatialContextSnapshotRow {
  id: string;
  chatId: string;
  messageId: string;
  swipeIndex: number;
  currentLocationId: string | null;
  definitionRevision: number;
  source: "bootstrap" | "owner_turn" | "assistant_swipe" | "definition_repair" | "branch_copy";
  transitionCommandId: string | null;
  transitionPayloadHash: string | null;
  createdAt: string;
}
```

必需的索引与不变量：

- 每个 `(chatId, messageId, swipeIndex)` 只有一行生效记录。
- 转移命令 ID 非空时，在其所属聊天内唯一。
- 同一个命令 ID 若携带了不同的目的地、期望修订号或期望当前地点，返回 `409 spatial_transition_command_mismatch`。
- 同一个命令 ID 若携带完全相同的内容，返回 `409 spatial_transition_already_applied`，响应里带上已提交的快照和用户消息 ID，并且不做第二次写入。客户端据此对齐状态，而不是重发这一回合。
- 快照行使用稳定的地点 ID。改名和更换父节点都不会改写快照。
- 在存在已提交的消息锚点之前，启动引导行使用 `messageId: ""` 和备选回复索引 `0`。
- 删除聊天、消息或备选回复时，在当前维护 Game 快照和回合快照的同一批位置上，一并移除或移动对应的空间记录。

新表必须注册进文件表定义、文件后端表清单、级联关系图、档案备份与恢复，以及 Mari 数据库完整性元数据。查找行为必须有文件原生回归覆盖。

### 生效状态与历史规则

API、提示词、分支和客户端响应统一使用同一个解析器：

1. 如果请求指定了具体的消息和备选回复，就返回那份空间快照。
2. 对于当前视图，检查最新的可见 Assistant 消息及其当前生效的备选回复。
3. 如果那条 Assistant 备选回复没有对应记录，就按可见消息顺序向前找最近的用户回合快照或 Assistant 快照。
4. 再退回到启动引导行。
5. 如果一份快照都没有，而已启用的定义有合法的起始地点，就返回一个内存中的起始状态，并在第一次归属回合时把它落盘。

归属回合的锚定方式：

- 持久化之前，从当前可见的历史中解析出源状态，不要只按时间戳取最新那一行。
- 在原子的回合事务里，创建用户消息、首条备选回复、聊天时间戳，以及一份锚定到该用户消息的 `owner_turn` 空间快照。
- Assistant 回复保存之后，把同样的状态以 `assistant_swipe` 落到它的 `(messageId, swipeIndex)` 上。
- 服务商调用失败或中止时，已接受的用户回合及其空间快照仍保持提交状态。因此重新加载会显示这次移动和已保存的用户消息，而不会凭空造出一条 Assistant 回复。
- 重新生成时解析目标 Assistant 消息之前那一刻的状态，并把该状态写入新的备选回复。续写则沿用目标备选回复的状态。
- 选择某条备选回复时，生效状态通过已有的活跃备选回复记录发生变化。它不会改写其他快照。
- 创建分支时会复制定义，把复制过来的每份空间快照重新关联到新的消息 ID，并包含启动引导行。从更早的消息分支时，复制到选定的截断点为止。
- Game 存档点保存对应空间快照的 ID，或者保存其当前地点和定义修订号的稳定副本。加载存档点会同时恢复 Game 状态和空间状态。

定义的编辑不进入历史。改名或更换父节点会改变旧快照渲染出来的面包屑，因为稳定的地点 ID 是对着当前分支的定义解析的。旧快照可能指向一个已归档的地点；它依然可读，但下一个目的地必须是活跃且可达的节点。如果编辑操作归档了当前生效的地点，就必须提供 `replacementCurrentLocationId`，服务器会在写入新定义修订的同一事务里，于当前可见锚点处写下一份 `definition_repair` 快照。

### 原子的归属回合流程

给 `generateRequestSchema` 和客户端生成契约扩展一个可选的 `pendingSpatialTransition`。它只对 Roleplay 和 Game 归属聊天有效。

服务器的处理顺序是：

1. 获取已有的按聊天生成锁。
2. 在请求生命周期内解析请求并加载聊天。
3. 如果没有空间转移，保持原有的消息流程。
4. 如果存在转移，开启一个规模恒定的数据库事务。
5. 在事务内重新读取定义和可见状态。
6. 校验归属模式、启用状态、期望定义修订号、期望当前地点、命令 ID、目的地状态和可达性。
7. 通过绑定到该事务的聊天存储实例创建用户消息和首条备选回复。
8. 插入空间快照并更新聊天时间戳。
9. 对 Game 而言，条件允许时在同一事务里提交可见的 Game 快照。
10. 提交事务，然后在事务之外继续做附件加工、用户角色快照、提示词组装和服务商调用。

校验失败发生在把客户端的乐观状态当成权威之前。`400` 的图结构或目的地错误，以及 `409` 的状态过期错误，都会带上稳定的机器码、可安全展示给读者的文案、当前修订号和当前面包屑。它们绝不包含隐藏或阻断目的地的名称。

在服务器接受这一回合之前，客户端会一直保留已提交的文本、附件和待生效目的地。发生冲突时，客户端移除乐观消息、刷新 Spatial Context 查询、恢复草稿，并提供 `Review destinations`。被接受时，三者一起清除。

提示词上限与存储上限是两码事：

- 面包屑节点最多 20 个。
- 归属模式描述最多 4,000 个字符。
- 私有模型记忆最多 8,000 个字符。
- 目的地最多 50 个，按 `sortOrder`、名称、ID 的确定顺序排列，后面只跟一个略去数量。
- 在世界书处理器套用条目和 Token 预算之前，当前地点的世界书引用最多 50 条。
- 每个地点最多存 6 张视觉参考图；在服务商的参考总数上限之前，普通场景请求最多有 2 张地点参考候选。
- 分镜清单可以保留全部解析出的候选 ID 以供审计和刷新，但每个关键帧的实际内容都受创建清单时记录的服务商上限约束。
- 关联投影的 `awarenessSummary` 或退回使用的公开描述摘录最多 1,000 个字符。

由一个格式化器产出共享的结构化归属块。Roleplay 和 Game 各自在这个块外面套一层薄适配器。格式化器绝不序列化 `lorebookEntryIds`；归属模式的提示词流水线通过世界书处理器来消费它们。第二个格式化器只在阶段 3 引入，负责产出隐私收敛后的 Conversation 块，并且拿不到任何地点世界设定字段。

每条实时路径都在最终准备模型请求之前，调用同一个解析器和格式化器：

- 标准的 Roleplay 生成。
- Game 的 GM 生成。
- `/api/generate/dryRun`。
- 没有精确保存请求时的实时 Peek Prompt 组装。
- 需要重建提示词的重试和续写路径。

精确的缓存 Peek Prompt 不需要重新组装。它显示的是已经保存下来的那份服务商请求，其中必须含有该条备选回复当时用的空间块。回归覆盖必须对同一份夹具数据，比较实时生成、试运行和实时 Peek Prompt 三者归一化后的空间块。

### 基于世界书的草稿契约

地图取材是一项显式的编辑输入：

```ts
interface SpatialMapGroundingRequest {
  mode: "setup_only" | "lore_strict" | "lore_expand";
  lorebookIds: string[];
  entryIds?: string[];
}
```

Game 设置流程的 `lorebookIds` 默认取自 `GameSetupConfig.activeLorebookIds`。Roleplay 则默认取自当前聊天的全局、已关联和已固定的世界书。创作者可以在生成之前修改选择。已禁用或被显式排除的世界书和条目永远不会发出去。

这不是一次世界书激活扫描。服务器直接读取选定的来源，对着归属模式的设置上下文解析支持的宏（解析结果不落盘），并构建一份目录，其中包含：

- 临时来源键
- 条目和世界书名称
- 激活关键词和标签
- 条目描述（如有）
- 否则是一段长度受限的内容摘录

目录规模取三者中的最小值：100 个条目、16,000 个字符，以及为设置、系统和期望输出预留空间之后连接所剩的上下文。优先级是确定的：

1. 显式选中的 `entryIds`。
2. 标签、名称或关键词带有地点特征的条目。
3. 写了描述的条目。
4. 其余条目，按世界书和条目的稳定顺序排列。

如果有条目被略去，预览会报告数量并提供细化来源的入口。它绝不会让人误以为整本世界书都纳入了考虑。

简化后的模型方案会给每个提议地点加上临时来源键。服务器拒绝未知的键，把有效的键映射成稳定的条目 ID，去掉重复项，并计算预览用的来源标注：

- `Lore-backed`：至少有一条经过校验的来源条目。
- `Inferred`：某种关系或包含关系来自源材料，但源材料里没有独立条目与之对应。
- `Added by AI`：没有任何来源条目支撑这个节点。

`lore_strict` 会拒绝每一个没有有效来源键的节点。`lore_expand` 接受推断和新增的节点，但会明显标注出来。有效的来源键只能证明出处，不能证明语义准确，所以预览必须展示来源摘录，让创作者在应用之前就能发现误读的关系或名称。

生成接口返回归一化后的草稿定义，外加一份以生成地点 ID 为键的临时来源标注表。保存之后只有 `lorebookEntryIds` 会持久化。替换和扩展仍保留原有的历史保护措施；扩展可以给新节点添加绑定，但不能改写已有的地点或绑定。

### Game 兼容性边界

当某个 Game 聊天启用了 Spatial Context 之后：

- `SpatialContextSnapshot.currentLocationId` 是权威。
- Game 状态里的 `location` 仅作兼容投影。
- Game 状态的 GET 响应和追踪器界面拿到的是解析出的面包屑，作为显示用的地点。
- 世界状态智能体补丁和手动的 Game 追踪器补丁都不能自行写入 `location`；服务器会丢弃该字段并留下一条调试诊断，或者对显式的手动编辑返回字段级冲突。
- 新的 Game 快照会把面包屑镜像到它原有的 `location` 值里，好让会话历史和已有界面继续可读，但提示词代码仍然读取空间投影。
- Game 地图、网格格子或节点都可以显式绑定到一个稳定的层级地点 ID。
- 选中已绑定的目的地会创建一次结构化的待生效空间转移，不会插入移动叙述文本。
- 未绑定的格子和节点移动仍属战术层面，只改变队伍位置。
- 进入已绑定的地点时，若有对应的局部地图就选中它；离开时，若有最近的已绑定祖先地图就选中它。
- 两套系统同时可见时，界面会分别明确标为 `Story location` 和 `Map position`。
- 关闭 Spatial Context 会立刻恢复当前原有的 Game 地点行为，且不删除空间定义或快照。

反向验证必须证明：模型发出的 Game 地点补丁、手动的追踪器编辑，以及点击未绑定的地图，都无法改变 `currentLocationId`。正向验证则证明：合法的绑定点击走的是常规的转移校验器。

### 归属模式界面契约

Chat Settings 只为 Roleplay 和 Game 增加一块紧凑的 `Hierarchical Map` 区域。它显示启用状态、当前面包屑、活跃与已归档数量、警告数量，以及 `Open Map Editor`。它不会把完整编辑器塞进抽屉里。

地点编辑器沿用现有的整页编辑器路由：

- 桌面端使用层级导航器、局部地图或分层视图，以及所选地点的详情面板。
- 移动端先显示层级、后显示详情，并提供可见的返回地点列表操作。任何操作都不依赖悬停或拖拽。
- 每一行都通过带文字标签的控件提供添加子地点、添加同级地点、更换父地点、复制子树、归档和链接操作。
- 局部视图把子地点渲染成带坐标的地图节点、有序的分层，或者一份可访问的列表。
- 选中只是预览地点；进入用单独的 Enter 操作。
- 详情面板包含名称、类别、公开描述、私有模型记忆、图标、呈现方式、坐标或分层序号、状态、父地点、直连链接和挂载的世界设定。
- 视觉标识是详情面板里的内联区域，不是阻塞式窗口。它先显示主图预览，然后是辅助参考图、角色、用法备注、继承状态、断裂状态和图片来源元数据。
- 图库选择和上传复用现有的图片控件。`Generate establishing reference` 会打开一个预览；接受图片和把它设为主图都是明确的独立操作。
- 生成的场景图在它原有的图片操作里提供 `Set as location reference`。绝不会仅仅因为场景是在那里生成的，就改动这个地点。
- 挂载世界设定用的是内联可搜索的展开区域，而不是阻塞式窗口。搜索结果按世界书分组，并在挂载之前就标出禁用或排除状态。
- 已挂载的每一行都提供打开条目和解除挂载。解除挂载不会删除世界设定内容，复制子树会连同绑定一起复制。
- 世界书编辑器会显示当前聊天里的地图反向链接，方便创作者找出用到某条条目的每一个地点。
- AI 草稿控件会显示来源世界书、取材模式、已考虑和已略去的条目数量以及来源标注，读者不需要懂提示词技术细节。
- 校验提示既内联显示，也在保存附近汇总。点选汇总项会定位到对应的节点和字段。
- 编辑器使用本地工作副本和一个带修订号的保存操作。`editorDirty` 会拦住误离开的导航。服务端冲突时保留工作副本，并提供重新加载服务器版本或查看差异；不存在盲目覆盖。
- 空状态直接教第一步该做什么：`Create a starting location`。在存在合法且活跃的起始地点之前，无法启用该功能。
- 加载态沿用现有的编辑器骨架屏样式。保存、冲突、已归档、隐藏、阻断和无效状态除了颜色之外，还用文字或图标区分。

归属模式的聊天界面共用 `SpatialContextRuntimeBar`：

- 已持久化的面包屑显示在输入框上方或旁边，不遮挡故事内容。
- 目的地选择器分组列出父地点、子地点和直连链接，并保持确定的顺序。
- 选中目的地会生成一个标注清晰的待生效标记。它不会立刻改变状态。
- 这个标记可以清除，并且会随文本草稿一起在切换聊天或重新加载后留存。
- 发送内容可以是文本、附件，也可以只有一个待生效目的地。转移属于请求数据，不会追加进可见的消息文本。
- 冲突之后，过期的待生效目的地仍然可见并标为 `Needs review`，直到用户改选一个有效目的地或清除它。
- 窄屏上面包屑从中间截断，保留当前地点名称，并通过可访问的展开控件显示完整路径。

编辑器和运行时控件使用现有的语义主题变量，支持深色、浅色和 SillyTavern 主题，移动端主要操作保持 44px 的触控区域，并带有可见的焦点状态。动效限制在 150 到 250 ms 的状态过渡，绝不为了装饰而移动布局。

### 可移植性与生命周期覆盖

Marinara 的原生聊天导出必须带上：

- `marinara_metadata` 中的当前定义。
- 以导出后的消息序号和备选回复索引（而非显示名称）为键的空间快照。
- 存在时的启动引导快照。

导入会新建聊天 ID、消息 ID 和快照 ID，同时保留定义内部的地点 ID。导入的图如果格式有问题，就关闭 Spatial Context、保留原始定义供修复，并返回警告。绝不会悄悄按名称匹配，也不会只启用一部分。

聊天 JSONL 导出会保留地点到条目的 ID，因为它们本来就是定义的一部分，但不会顺手打包世界书内容。导入时会对着目标档案解析引用，并把缺失的条目报告成可修复的警告，不做名称匹配。档案备份与恢复能保住可用的引用，因为它同时带上了空间定义和世界书表。将来可能会有明确的战役包，为跨档案迁移打包相关世界书。

聊天 JSONL 同样会保留地点到图片的 ID、角色、用法备注和排序，但不内联图片字节。导入时会对着目标档案解析这些 ID，把缺失的图片报告成可修复的警告，不做路径或文件名匹配。档案备份与恢复包含档案图库的记录和文件。将来可能会有明确的战役包提供 `Include location images`，并在导出前给出素材数量、总大小和授权提醒。

导出或复制已有的分镜生命周期时，它的视觉清单会保留来源消息序号和备选回复、解析出的地点 ID、候选图片 ID 和关键帧顺序，但不嵌入字节。导入会重新映射消息 ID 和分镜 ID，在目标档案里解析图库图片 ID，并把缺失的素材标记为 `needs_review`。没有清单的旧分镜会在第一次重新生成时，从它保存的来源消息和备选回复解析出一份；它们绝不会退回到名称匹配或聊天最新地点。

档案备份与恢复通过 `FILE_BACKED_TABLES` 纳入新表。删除聊天、批量删除、彻底清除、删除分支、删除备选回复和删除消息都沿用现有的级联与应用层清理路径。已有的聊天无需急着迁移，因为没有相应元数据就等于 Spatial Context 未启用。

### 工作包与合并顺序

#### 工作包 A：核心契约与验证性试做

- 添加共享类型、schema、纯函数式图辅助函数、上限、夹具数据和稳定的错误码。
- 添加一个临时的验证工具，用来在文件原生存储上验证规模恒定的事务。不要保留 `.test.ts` 文件。
- 用启动引导、可见备选回复、更早的分支点、历史当前地点已归档、定义过期这几组夹具数据验证状态解析器。
- 测量浅层、深度 20、宽度 500、长文本和带链接这几类图的投影体积。

关口：在界面工作开始之前，图语义、投影上限、快照锚点和事务可行性都已得到验证。

#### 工作包 B：定义 API 与存储

- 添加表结构、迁移、文件后端注册、存储适配器、GET 以及带修订号的 PUT。
- 为归档操作添加当前地点替换。
- 接好删除、备选回复索引移动，以及档案备份与恢复。
- 为修订冲突、非法图、隐藏项错误和命令复用添加服务端回归覆盖。

关口：定义和快照在两种存储后端上都能完整往返，非法写入不留下任何部分状态。

#### 工作包 C：归属回合的历史集成

- 为生成请求扩展 `pendingSpatialTransition`。
- 添加原子的归属回合持久化和 Assistant 备选回复状态落地。
- 集成重新生成、续写、活跃备选回复、分支和 Game 存档点。
- 添加定义和快照的原生聊天导出导入。

关口：重新加载、服务商调用失败、切换备选回复、从更早的消息分支、导入导出和存档点恢复，都能解析出预期的地点。

#### 工作包 D：提示词投影与 Game 权威归属

- 添加结构化投影和长度受限的格式化器。
- 集成实时生成、Game GM、试运行、实时 Peek Prompt、重试和续写。
- 落实 Game 兼容性边界和追踪器的面包屑显示。
- 添加隐私和非活跃地点的反向验证。

关口：所有提示词路径都含有相同的空间块，没有无关地点文本泄漏，Game 也无法自己维护一个相互竞争的权威地点。

#### 工作包 E：地图浏览器与编辑器

- 添加 React Query hook、冲突映射、设置摘要和懒加载的编辑器路由。
- 添加层级、局部地图、分层、列表、预览、详情面板和复制子树等工作流。
- 添加桌面端和移动端的无障碍状态。
- 修订冲突时保住未保存的编辑内容。

关口：创作者无需拖拽、悬停或精细操作就能搭建和修复嵌套地图。

#### 工作包 E.1：AI 辅助地图起草

- 添加一个按需触发的设置时生成器，它使用范围受限的 Game 或 Roleplay 设置上下文，绝不在回合过程中隐式改动数据。
- 先生成一份带键的简化地图方案，再分配稳定 ID、修补安全范围内的布局缺项，并在服务端校验完整定义。
- 在替换编辑器状态之前，先把生成的层级作为本地草稿预览。
- 要求明确的应用和保存操作；生成本身既不会启用 Spatial Context，也不会自行写入定义。
- 生成提示词里不带普通聊天历史，并通过调试日志暴露最终提示词。

关口：不懂技术的创作者可以描述一个世界，拿到合法的嵌套地图，仔细查看，并在保存之前拒绝或应用它，期间持久化状态不变。

#### 工作包 E.1.1：历史安全的 AI 地图扩展

- 把整图 AI 生成当作开局前的工作流。一旦存在与消息关联的空间历史，服务端就要保住每一个已有的地点 ID。
- 在战役进行中，把整图生成器换成限定于某个选中活跃地点的仅追加扩展流程。
- 保留当前地点、起始地点、已有的描述、链接、布局、已归档节点和后续的 Game 绑定。只为新增的地点分配新的稳定 ID。
- 扩展仍基于范围受限的设置上下文和所选地点上下文，而不是普通的回合历史。
- 把新地点作为本地草稿预览，并保留现有的应用与保存这道分界线。
- 只有在还没有已提交的空间历史时才允许整图替换；地图已存在时，扩展是更安全的默认选项。

关口：AI 可以为进行中的战役扩充地图，同时不会让回合快照失去指向、不会改变当前地点、也不会替换已有的 ID。

#### 工作包 E.2：Game 设置向导的地图选项

- 在现有的功能步骤里加一个可选的 `Draft a hierarchical world map`，附带一个简单的规模选择。
- 只有在 `/game/setup` 已经持久化世界概览和故事线之后才运行地图生成。不需要先玩一个回合。
- 在生成后续草稿期间，设置流程要保持明显的忙碌状态，包括应用了修复后的设置数据之后。
- 生成完成后打开常规的 AI 预览和地图编辑器。跳过会回到游戏，应用只改动工作副本，保存仍是持久化的分界线。
- 如果地图生成失败，保留已经成功创建的游戏，说明失败原因，让创作者之后从 Chat Settings 里再建地图。
- 不要把完整地图编辑器塞进狭窄的设置向导，也不要悄悄启用并持久化生成出来的定义。

关口：创作者可以在设置过程中要一张更丰满的初始地图，既不会基于残缺的本地向导状态生成，也不会绕过审阅。

#### 工作包 F：Roleplay 与 Game 的运行时界面

- 添加共享的运行时栏，以及按聊天保存的待生效转移。
- 在不改动可见消息文本的前提下，接入 Roleplay 和 Game 的发送路径。
- 添加明确的 Game 地图、格子和节点绑定控件。
- 转移被接受后选中已绑定的地图，同时保住未绑定的战术移动。

关口：Roleplay 和 Game 都能移动、从过期状态恢复、重新加载、切换聊天，并且用键盘和触摸都能操作。

#### 工作包 F.1：地点世界书绑定与运行时激活

- 为共享 schema 和编辑器工作副本扩展长度受限的 `lorebookEntryIds`。
- 添加内联的地图挂载控件、世界书反向链接和断裂引用警告。
- 为共享的世界书处理扩展强制候选 ID、激活来源去重、排除规则和预留的地点设定上限。
- 把同一个解析器集成进 Roleplay、Game GM、试运行和实时 Peek Prompt 路径。
- 添加 Active Context 的来源和截断报告。
- 让引用 ID 在分支和 JSONL 导入导出流程中得以保留，目标缺少世界设定时给出警告。

关口：在各条归属模式提示词路径上，地点之间的移动只会激活目的地已启用的挂载世界设定，不会重复注入，也不会泄漏到 Conversation。

#### 工作包 F.2：基于世界书的地图起草

- 为创建、替换和扩展请求加上取材模式和显式的来源选择。
- 从选定的世界书构建体积受限的来源目录，而不是扫描普通聊天。
- 校验临时来源键，并把有效条目自动绑定到生成的节点上。
- 在草稿预览里显示 Lore-backed、Inferred 和 Added by AI 的来源标注，并支持查看来源。
- 在 Strict canon 下强制节点必须有出处，在 Canon with expansion 下让没有依据的添加清晰可见。
- 保留历史安全的仅追加扩展，以及现有的先应用后保存这道审阅分界线。

关口：选定的世界书事实直接为生成的层级提供依据，每一处没有依据的地点在保存前都清晰可见，严格模式下也无法持久化没有引用的生成节点。

#### 工作包 F.3：地点视觉标识与场景美术参考

- 为地点 schema 和编辑器工作副本添加长度受限的视觉标识文本和稳定的档案图库绑定。
- 添加内联的视觉标识编辑器、主图与辅助图角色、显式的风格继承、图库反向链接和断裂引用修复。
- 添加按聊天设置的 Illustrator 与 Game 两个并列的服务商使用开关，首张主图需明确同意，默认关闭以保证向后兼容。
- 添加按需生成的定场参考图，以及对已审阅生成场景的显式提升。
- 为 Roleplay Illustrator 和 Game 场景美术请求解析出对应消息和备选回复的地点。
- 在每家服务商现有的上限下，确定性地合并显式、地点、角色、用户角色和继承风格候选，并给出可见的略去原因。
- 让 ID 和元数据在分支和 JSONL 中得以保留，把二进制文件纳入档案备份与恢复，并添加故事提示词和 Conversation 的反向验证。

关口：同一地点反复出图时可以复用已审阅的场所标识，与角色参考之间的取舍确定且可见；历史消息的美术会解析到它当时的地点；任何仅供视觉使用的数据都不会泄漏进文本提示词。

### Issue 与 pull request 的边界

按仓库工作流，这是一项大型功能。在工作包 A 开始实现之前：

1. 确认或新建那一个总跟踪 issue，并在上面标明归属。
2. 检查是否已有与该 issue 关联的分支、草稿 pull request 或项目看板条目。
3. 实现一开始就针对 `staging` 开一个草稿 pull request。
4. 条件允许时，用工作包作为可审阅的 PR 边界；不要为了减少 PR 数量，就把归属模式 MVP 和关联 Conversation 合在一起。

建议的 issue 拆分：

1. Spatial Context 共享核心、持久化和定义 API。
2. 归属回合快照、备选回复、分支、存档点和可移植性。
3. 归属模式提示词投影与 Game 兼容性。
4. 归属模式编辑器与运行时移动界面。
5. 地点世界书绑定与归属模式运行时激活。
6. 基于世界书的地图起草。
7. 地点视觉标识与场景美术参考解析。
8. 分镜冻结视觉参考清单。
9. 关联 Conversation 的只读投影。
10. 由模型发起的移动。

## 验收标准

- 地图地点存的是世界书条目引用，绝不是复制过来的世界设定内容。
- 地点存的是可选的视觉标识元数据和稳定的图库图片引用，绝不是原始路径、外部 URL 或图片字节。
- 图像风格方案控制渲染风格，地点参考控制场所标识，角色或用户角色参考控制主体标识。
- 符合条件的场景美术请求会解析出它那条消息和备选回复对应的确切地点，历史重试也一样，绝不按名称模糊匹配地点。
- 生成的美术只有在创作者明确操作之后才会成为地点参考。
- 布局参考绝不自动进入普通场景生成，也只有风格参考可以向下级继承。
- 文本提示词和关联 Conversation 拿不到任何地点视觉参考 ID、字节、路径或仅供图像使用的备注。
- 分镜从它的来源消息和备选回复解析地点，冻结自己的参考库和有序的关键帧内容，并在重新生成时一直复用，直到明确刷新。
- 每个分镜关键帧只为它解析出的地点和可见人物挑选参考，不在画面里的成员永远不占容量。
- 单名额和多名额服务商的行为确定且可见，更换服务商也绝不会悄悄添加、移除或替换已冻结的参考。
- 分镜清单存的是稳定 ID 和元数据，绝不是图片字节或文件系统路径。
- 没有清单的旧分镜绝不会拿地点名称匹配或聊天最新地点当作隐式修复手段。
- 只有被接受的确切当前地点才会强制激活挂载的世界设定，并且仍受禁用、排除、去重、排序、条目上限和 Token 预算规则约束。
- Active Context 会标明当前地点激活、组合激活来源和确定性的截断。
- 有依据的起草直接读取显式选定的世界设定条目，不依赖关键词扫描或生成出来的世界概览摘要。
- Strict canon 只产出有出处的地点；Canon with expansion 会在保存之前标出每一处推断或无依据的添加。
- 关联 Conversation 拿不到任何地点挂载的世界设定 ID 或内容。
- 改名和更换父节点都不改变地点的身份标识。
- 非法的图和过期的写入永远不会改动状态。
- 移动要么随用户回合一起提交，要么根本不提交。
- 重新加载、选择备选回复、从更早的消息分支和加载 Game 存档点，都能解析出正确的地点。
- 归属模式提示词只包含活跃地点的上下文和有效目的地。
- 启用之后，Game 不会显示、也不会用一个相互竞争的自由文本地点来生成提示词。
- 已有的 Game 地图可以显式绑定到层级地点，而不影响战术移动。
- Roleplay 和 Game 使用同一套层级和转移规则。
- 试运行和 Peek Prompt 与实际生成使用相同的投影行为。
- 已有的聊天以及未启用 Spatial Context 的情况都保持当前行为。
- Conversation 既不能拥有、也不能改动空间状态。
- 私有模型记忆永远不会进入 Conversation 投影。
